# init --demo First-Run Multi-Agent Demo

## Problem Statement

After `ai-devkit init`, new users have configuration and skills but no guided experience showing that AI DevKit can run multiple coding agents in tmux and exchange messages. Discovery requires reading `agent start` and `agent send` docs without a quick proof that the local harness CLIs and tmux are wired correctly.

## Goals and Non-Goals

### Goals

- Add `ai-devkit init --demo` to run after a successful init in the same invocation.
- Detect installed harness CLIs using the same registry as agent start (claude, codex, opencode, and the other `HARNESS_RUNTIME_PROFILES` types).
- Pick two distinct installed harnesses with a stable preference order (claude, then codex, then opencode, then the remaining startable types).
- Start a lead and a worker agent in tmux via the existing `startAgent` path (no new runtime).
- Run one scripted handoff with `agent send --wait`: surface a lead question and capture the worker reply in the transcript.
- Print a short summary (harness types, question, reply) and the next three commands to try.
- Fail clearly with exit code 1 when tmux is missing, when fewer than two harnesses are installed, or on unsupported platforms.
- Support macOS and Linux only; print an explicit unsupported message on Windows.

### Non-Goals

- No change to devkitd or daemon migration paths.
- No guaranteed fully autonomous lead→worker tool use inside harness UIs; the CLI orchestrates the deterministic worker prompt.
- No Windows/WSL auto-setup.
- No modification of generic skills with project-specific steps.

## User Stories

- As a first-time user on a Mac with Claude Code and Codex installed, I want `init --demo` to show two agents start and one reply so I trust the toolkit before opening the console.
- As a user missing tmux, I want an install hint and a nonzero exit before agents are started.
- As a user with only one harness, I want to know which CLI was detected and how to install another.

## Success Criteria

1. `init --demo` is documented on the `init` command and runs only after init completes successfully (exit 0).
2. Prerequisites are validated before any tmux session is created.
3. Two agents remain running with predictable names (`demo-lead`, `demo-worker`) and attach instructions match `agent start` UX (sessions are not auto-killed).
4. Unit tests in `packages/cli/tests/` mock harness detection and tmux; no real vendor CLIs required in CI.
5. E2E tests in `e2e/` cover failure paths for missing tmux and a single harness without real CLIs.
6. `fmt:check`, lint, and the full test suite pass.

## Constraints

- macOS and Linux only for the demo path.
- Use existing `commandExistsOnPath` / `HARNESS_RUNTIME_PROFILES` detection; do not fork harness lists.
- Reuse `startAgent`, `sendToAgent`, and tmux install copy from existing agent commands.
